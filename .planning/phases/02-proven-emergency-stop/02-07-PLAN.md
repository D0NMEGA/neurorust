<objective>
Wrap the measurement in the Phase 1 evidence machinery, so a STOP-07 run is admissible under the
same protocol every other published figure in this repository is.

Purpose. Plan 02-06 produces latency samples. A number is not a result in this project until it
carries the fifteen precondition results, the environment snapshot, the interference diff, per-file
checksums over its raw capture and a provenance tier that says how its own identity was obtained.
D-06 is the rule it is held to: the harness asserts preconditions and refuses to run on violation,
changing nothing about system state. A run that violates a precondition is refused, not footnoted.

Three things this plan decides, each recorded rather than assumed.

The harness writes its own run directory rather than importing one. `RunDir::create` and
`harness_info()` live in `crates/cli`, which declares only a `[[bin]]` target and no `[lib]`, so
nothing outside that crate can import them at any visibility. That is not a `pub` oversight to fix.
A local equivalent following the same `<YYYY-MM-DD>-<rig-slug>-<run-class>[-NN]` convention is
about forty lines, and the project's own rule is to copy twice before abstracting. Promoting
`RunDir` into `nr-manifest` is the right move when a third caller appears, not now.

The metrics entry is written into the run directory and nowhere else. D-37 is explicit: one
headline-class run, published with its raw capture, and the `emergency_stop.abort_latency` stage
does not enter the weekly series or the regression baseline in this phase, because a weekly series
taken against the D-33 stand-in would track the stand-in rather than the runtime. Writing the
entry proves D-04's claim that the schema generalises, which
`crates/metrics/tests/series.rs` already round-trips with this exact stage and tool string.
Appending it to `metrics/latency-series.json` would be a different and wrong thing.

The rig entry point is extended rather than duplicated. `scripts/nr-run-measurement` already holds
the NOPASSWD sudo grant, the group-writable binary refusal, the sha256 record, the concurrent-run
refusal and the `TimeoutStartSec` backstop that exists because a runaway held `SCHED_FIFO` 99 on
the isolated cores for 24 minutes on 2026-09-04. A second script would either duplicate all of that
or quietly do without it. The sudoers grant names the script path and passes arguments, so adding a
subcommand needs no sudoers change at all.

Runs entirely on the macOS dev host. The rig run is plan 02-08.

Output: `nr-stop-harness` produces a run directory `nrmeasure verify --strict --check-index`
accepts, and the whole pipeline is exercised end to end on macOS against fixtures.

    instrument_class: InstrumentClass::HeadlineSeries,

`target_cpus` is the two cores the run actually uses, not the whole isolated set. The isolcpus
check asks whether `isolcpus` covers the targets and the C-state check reads those cpus, so naming

refusal rather than a pass. The clock characterisation is `RunClass::Recon` because it is not a
latency figure, but it is published beside one, so it is held to the same evidential bar.

<threat_model>
## Trust boundaries

This plan connects the harness to the repository's evidence machinery and opens a root-adjacent
entry point on the rig. Two real boundaries appear here that did not exist in plan 02-06.

| Boundary | Description |
|----------|-------------|
| a fixture run -> a published capture | A run taken against fixtures must never be readable as a rig measurement. |
| operator argv -> a root script under NOPASSWD sudo | `nr-run-measurement` runs as root without a password, so anything it takes from argv is a root action at a caller-chosen target. |
| a raw capture file -> the verify gate | A capture the gate does not recognise is a capture the gate cannot notice going missing or being copied. |
| the harness process -> the rig's measurement state | The run must observe the machine and change nothing about it (D-06). |
