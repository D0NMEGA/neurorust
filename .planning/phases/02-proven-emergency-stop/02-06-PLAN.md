<objective>
Build the part of the STOP-07 harness that does the measuring: the clock, the scheduling setup, the
stand-in hot path, and the percentile computation. Everything here runs and is tested on the macOS
dev host. The rig comes later.

Purpose. STOP-07 asks for a bounded, measured abort latency on the reference rig. D-31 defines the
interval precisely: from the timestamp the aborting thread takes immediately before the latch
store, to the timestamp the hot-path thread takes at the iteration where it first observes the gate
closed. That is the last moment a sample could still have flowed. Timing the store alone would
produce a flattering number with no safety meaning, and ending at a real sink output needs a
decoder that does not exist until Phase 6.

Three design points are already decided and this plan implements them rather than revisiting them.
The hot path checks the latch once per node iteration at a fixed point in the loop (D-32), so the
latency is bounded by one iteration plus cross-core propagation. The stand-in is a single thread on
one isolated core running a fixed-period loop whose only body is the poll (D-33), so the
measurement isolates the two terms D-34 reports. Both ends read `CLOCK_MONOTONIC_RAW` (D-35), which
is not what `std::time::Instant` uses on Linux, so this needs an explicit `clock_gettime` call.

D-35 also asks for something separate and it is a separate deliverable, not a footnote: the clock's
own read overhead and the cross-core offset between the two threads are characterised in their own
capture and published beside the figure, so the number carries its own instrument error rather than
assuming it away. That is `characterise.rs` here and its own run directory in plan 02-08.

Dependency direction, from D-55 and not negotiable: `nr-stop-harness` depends on `nr-stop`,
`nr-histogram`, `nr-metrics`, `nr-capture` and `nr-manifest`. Nothing in any of those five gains a
dependency on `nr-stop` or on this harness. The one change this plan makes inside a measurement
crate is additive and has nothing to do with the runtime: `nr-histogram` gains a function that
computes percentiles from a flat slice, which any caller with raw samples can use.

One thing this plan deliberately does not reuse, because reading the code shows it cannot.
`RunDir::create` and `harness_info()` live in `crates/cli`, which declares only a `[[bin]]` target
and no `[lib]`, so nothing outside that crate can import them at any visibility. A small local
equivalent is the right amount of new code, and plan 02-07 writes it. Do not add a `[lib]` target
to `crates/cli` to make the import possible.

Runs entirely on the macOS dev host. No rig, and nothing published.

Output: a `nr-stop-harness` binary that produces raw latency samples and a clock characterisation,
with the platform-independent half of both covered by tests that run on macOS.

//! on one code path has none of that structure, so this module takes the samples directly.
//!
//! Same machinery, same philosophy. The percentiles come from `hdrhistogram`, exactly as
//! `CyclictestRun::percentiles` does, so the two cannot drift on rounding. The minimum and the
//! maximum are taken from the slice itself rather than from the histogram, matching the rule
//! already documented on `CyclictestRun::max_us`: the worst case is exact, never a bound.

use hdrhistogram::Histogram;

use crate::percentiles::PercentileError;

/// hdrhistogram significant figures for raw sample statistics.
///
/// Five, not the three `percentiles.rs` uses. That constant is documented as keeping single digits
/// to low thousands of MICROSECONDS exact. These samples are nanoseconds: a 33 microsecond poll
/// period is 33_000 ns, where three significant figures would quantize to the nearest 33 ns and

//! exercised by cargo test on the macOS CI leg rather than cfg'd out of existence. This is the
//! same shape nr-capture uses for SystemFacts with LiveFacts and FixtureFacts.
//!

//! CLOCK_MONOTONIC_RAW. D-35 requires the raw clock at both ends, which is also the project's

//! means. That requires an explicit clock_gettime call.

    /// cannot be read at all, which every caller must treat as a refusal to produce a figure

    fn now_ns(&self) -> Option<u64>;
}

/// The real clock.
#[derive(Debug, Clone, Copy)]
pub struct RawClock;

**`crates/stop-harness/src/characterise.rs`.** This is D-35's second deliverable and it is not a
footnote on the first. Three measurements, each with its own function, each returning raw samples
rather than a summary so the caller can put them through `stats_from_samples`:

  1. `pub fn read_overhead_ns<C: MonotonicRawClock>(clock: &C, iterations: usize)
     -> Result<Vec<u64>, CharacteriseError>`. Take `iterations + 1` readings in a tight loop with
     nothing between them, and return the consecutive deltas. Each delta is one clock read plus one
     loop iteration, which is what a caller of this clock actually pays. Say that in the doc
     comment rather than calling it "the syscall cost", which it is not: `CLOCK_MONOTONIC_RAW` has
     been vDSO-accelerated since Linux 5.3 and the rig is far past that, so the expectation is tens
     to low hundreds of nanoseconds and the point of measuring is that it is measured.
  2. `pub fn cross_core_offset_ns<C>(clock: &C, cpu_a: usize, cpu_b: usize, rounds: usize)
     -> Result<Vec<i64>, CharacteriseError>`. Two threads pinned to the two cpus exchange a
     timestamped ping-pong over a shared `AtomicU64` sequence number, recording T1 (A's send), T2
     (B's reading on receipt) and T3 (A's reading on the reply). The offset estimate is
     `((T2 - T1) + (T2 - T3)) / 2`, computed in `i64` with `i64::try_from` on each reading so no
     subtraction can underflow a `u64`. Return one estimate per round.
     The doc comment must say plainly what this is: a Cristian's-algorithm round-trip offset
     estimate, a well-known general technique applied here by analogy, with no source specific to
     same-machine invariant-TSC cross-core skew. It assumes symmetric propagation delay, and that

**The shape.** One configuration struct and one entry point:

```rust
pub struct TrialConfig {
    /// The node iteration period. The latch is polled once per iteration at a fixed point in the
    /// loop (D-32), so this is one of the two terms D-34 reports separately.
    pub period_ns: u64,
    pub trials: usize,
    pub hot_cpu: usize,
    pub abort_cpu: usize,
    pub priority: u8,
    /// Seed for the abort-phase sequence, recorded so a run is reproducible.
    pub seed: u64,
}

pub struct TrialOutcome {
    /// One row per trial: the phase within the period at which the abort was raised, the two raw
    /// clock readings, and their difference. Every column is recorded so a reader can re-derive
    /// the latency rather than trust it.
    pub rows: Vec<TrialRow>,
}

pub struct TrialRow {
    pub trial: u32,
    pub phase_ns: u64,
    pub abort_raw_ns: u64,
    pub observed_raw_ns: u64,
    pub latency_ns: u64,
}

pub fn run_trials<C: MonotonicRawClock + Sync>(
    clock: &C,
    config: &TrialConfig,
) -> Result<TrialOutcome, TrialError>;
```

Generic over the clock rather than taking a trait object, so the real clock's read inlines and the
macOS tests still exercise the same loop through `FixtureClock`.

**The loop.** Preallocate everything before the first trial: a `Vec<EmergencyStop>` of length
`config.trials` and a `Vec<TrialRow>` with `with_capacity(config.trials)`. Both allocations happen
before the measurement begins, which is what the hot-path rule requires; allocating between trials
would put the allocator inside the thing being measured.

Use `std::thread::scope` with two threads. Each pins itself with `sched::pin_current_thread` and
requests `SCHED_FIFO` with `sched::request_fifo` before the first trial. Synchronise the two
threads per trial with a `std::sync::Barrier`. A barrier uses a mutex and a condvar, which the
hot-path rules forbid; it is used between trials and never inside the measured interval, and that
must be said in the module doc rather than left for a reviewer to notice and worry about.

The hot thread, per trial:

```
barrier.wait()
loop {
    // the fixed point in the iteration where the latch is polled, D-32
    if stop.state() != State::Running {
        let observed = clock.now_ns().ok_or(TrialError::ClockUnavailable)?;
        stop.acknowledge();
        record observed;
        break;
    }
    // busy-wait to the next period boundary; no sleep, because a blocking syscall here would
    // measure the scheduler's wakeup rather than the latch's propagation
    while clock.now_ns()... < next_deadline {}
}
```

The abort thread, per trial:

```
barrier.wait()
let phase = next_phase(&mut rng) % config.period_ns;
busy-wait phase nanoseconds
let at = clock.now_ns().ok_or(TrialError::ClockUnavailable)?;
stop.abort(Cause::Operator, at);
```

`at` is read immediately before the latch store and nothing happens between the two. That is
D-31's start point, and anything inserted between them, a log line, a bounds check, a debug
assertion, silently inflates the published figure.

**The phase generator.** A xorshift64star implemented in this file, seeded from `config.seed`. No
`rand` dependency: the requirement is a uniform phase within a period, this is eight lines, and
adding a dependency with a transitive tree for it would be the opposite of the project's
don't-hand-roll rule, which is about not reimplementing hard things rather than about never writing
eight lines. Say in the doc comment that it is not a cryptographic choice and does not need to be.

**Recording the phase matters.** D-34 publishes a worst case "taken from a uniformly random abort
phase". Recording every phase turns that from an assertion into something a reader can check
against the raw capture, which is the same move `nrmeasure verify --strict` already makes for
cyclictest percentiles.

**Sizing.** A `TrialRow` renders to roughly 55 bytes of TSV. `MAX_IN_REPO_FILE_BYTES` is 25 MiB,
so a single capture file holds roughly 470,000 rows before the run directory logic would push it
behind an external pointer, and `MAX_IN_REPO_RUN_BYTES` is 100 MiB for the whole directory. Default
`--trials` to 200_000 so two periods fit comfortably in one run directory with room for the
manifest and the report. Put that arithmetic in the flag's help text, so whoever raises it on the
rig knows what they are trading.

**Two periods, not one.** Claude's discretion under D-34 covers the poll period and whether more
than one is measured. Measure two and report them separately: 33_000 ns, which is one frame period
at the project's own 30 kHz target rate, and 1_000_000 ns, a 1 kHz node. Two periods let a reader
see the poll period's contribution directly, which is exactly the decomposition D-34 asks to be
published beside the total and never subtracted from it. The `abort-latency` subcommand takes
`--period-ns` and is run twice rather than looping internally, so each period gets its own raw
capture and its own row in the published table.

## Trust boundaries

This plan produces the numbers a published latency claim will rest on. It has no network surface
and no user input beyond command-line flags the operator supplies. The threats are about a number
that looks measured and is not.

| Boundary | Description |
|----------|-------------|
| the clock -> a published figure | Every number here is a difference of two clock readings, so what the clock is and what it costs to read decides what the figure means. |
| the harness process -> the machine it measures | Pinning and scheduling policy change the thing being measured, so a silent failure to apply them changes the number without changing the claim. |
| a raw capture -> a reader re-deriving the figure | The capture is the evidence, and a capture that cannot reproduce the figure is not evidence. |
| this crate -> the five measurement crates | D-55 fixes the dependency direction, and reversing it would make the measurement tooling depend on the runtime it measures. |
