<objective>
Prove the state machine, and commit the proof result as evidence.

Purpose. STOP-04 is the phase's differentiating artifact and the first half of the project's
stated core value. This plan writes the four harness families D-46 enumerates and runs them to
completion on the dev host, which is where they run: Kani's install guide lists
`aarch64-apple-darwin` as supported, so the full proof loop is local and fast.

What the four families buy, stated precisely, because the phase already corrected this claim once.
Families 1 through 3 are STOP-01, STOP-02 and STOP-03 mechanically: totality over the enumerated
space, no path back to `Running`, and no permit outside `Running`. Family 4 is what STOP-04
honestly buys in safe Rust: no reachable panic, no reachable arithmetic overflow, no reachable
index panic, no reachable `unwrap`. It is not the absence of undefined behaviour. The crate
contains no `unsafe`, so the compiler already excluded most of that before Kani ran, and D-47
amended both STOP-04's requirement text and ROADMAP criterion 3 on 2026-09-14 (commit af4c479) to
say so. That amendment is already done; this plan does not repeat it and must not re-edit either
document.

The second deliverable is D-54. A proof is committed evidence, not a green check that disappears
with the CI log. `docs/proofs/emergency-stop-proof-report.md` names the Kani version, every
harness and its outcome, and is generated from a real solver run by a committed script rather than
maintained by hand beside the thing it describes. That follows the project's existing habit (D-12)
of a generated human-readable report beside a machine-readable source of truth.

Discretion exercised here, recorded rather than left implicit. The report regenerates on demand,
not on every CI run. D-54 says the report is refreshed deliberately and reviewed like any
published claim under D-07, and a file that rewrites itself on every push is neither deliberate
nor reviewed. Instead the report records the commit it was generated from, so a reader can see for
themselves whether it describes the tree in front of them.

Runs entirely on the macOS dev host. No rig, nothing measured.

Output: ten harnesses across four families, all verifying, and a committed report saying so.

Family 1, STOP-01, totality. Four harnesses:

`step_is_total`. Over every state and every event at once, `step` returns one of the three
enumerated states.

```rust
#[kani::proof]
fn step_is_total() {
    let state: State = kani::any();
    let event: Event = kani::any();
    let next = step(state, event);
    assert!(matches!(next, State::Running | State::Stopping | State::Stopped));
}
```

This is totality: not "these six cases work" but "no input produces anything else", which is the
difference between a table of examples and a proof.

`state_raw_round_trips`. The wire encoding the latch stores round trips, so the atomic
representation and the enumerated space describe the same three states.

```rust
#[kani::proof]
fn state_raw_round_trips() {
    let state: State = kani::any();
    assert!(State::from_raw(state.as_raw()) == state);
}
```

`state_from_raw_is_total_and_fails_closed`. `from_raw` is total over every `u8`, not just over the
three values this crate writes, and every out-of-range value decodes to `Stopped`: the most
restrictive state, so a corrupted encoding fails closed rather than reopening a stopped session.

```rust
#[kani::proof]
fn state_from_raw_is_total_and_fails_closed() {
    let raw: u8 = kani::any();
    let decoded = State::from_raw(raw);
    assert!(matches!(decoded, State::Running | State::Stopping | State::Stopped));
    kani::assume(raw > 1);
    assert!(decoded == State::Stopped);
}
```

`cause_raw_round_trips_and_is_total`. The same two properties for the cause encoding, whose
out-of-range value decodes to `InternalFault`.

```rust
#[kani::proof]
fn cause_raw_round_trips_and_is_total() {
    let cause: Cause = kani::any();
    assert!(Cause::from_raw(cause.as_raw()) == cause);
    let raw: u8 = kani::any();
    let decoded = Cause::from_raw(raw);
    assert!(matches!(
        decoded,
        Cause::Operator | Cause::WatchdogDeadline | Cause::InternalFault | Cause::Shutdown
    ));
}
```

Family 2, STOP-02, the latch property. Three harnesses:

`abort_never_returns_to_running`. From any state at all, and for any cause and any timestamp, an
abort lands in `Stopping` or `Stopped` and never in `Running`.

```rust
#[kani::proof]
fn abort_never_returns_to_running() {
    let state: State = kani::any();
    let cause: Cause = kani::any();
    let at_raw_ns: u64 = kani::any();
    let next = step(state, Event::Abort { cause, at_raw_ns });
    assert!(next != State::Running);
    assert!(next == State::Stopping || next == State::Stopped);
}
```

`running_is_never_reachable_from_stopping_or_stopped`. Once out of `Running`, no event of any kind
returns to it. This is the structural form of the guarantee: it holds because there is no edge,
not because nothing calls a reset (D-39).

```rust
#[kani::proof]
fn running_is_never_reachable_from_stopping_or_stopped() {
    let state: State = kani::any();
    kani::assume(state != State::Running);
    let event: Event = kani::any();
    assert!(step(state, event) != State::Running);
}
```

`stopped_is_terminal`. Every event leaves `Stopped` where it is (D-39).

```rust
#[kani::proof]
fn stopped_is_terminal() {
    let event: Event = kani::any();
    assert!(step(State::Stopped, event) == State::Stopped);
}
```

Family 3, STOP-03, the gate invariant. Three harnesses:

`no_permit_when_not_running`. No permit is issued from `Stopping` or from `Stopped`.

```rust
#[kani::proof]
fn no_permit_when_not_running() {
    let state: State = kani::any();
    kani::assume(state != State::Running);
    assert!(!would_issue_permit(state));
}
```

`permit_supply_closes_on_the_abort_edge`. The supply closes on the abort edge itself, not on
reaching `Stopped` (D-40). From any state, the state an abort lands in issues no permit. This is
the property that makes safety independent of anything acknowledging.

```rust
#[kani::proof]
fn permit_supply_closes_on_the_abort_edge() {
    let state: State = kani::any();
    let cause: Cause = kani::any();
    let at_raw_ns: u64 = kani::any();
    assert!(!would_issue_permit(step(state, Event::Abort { cause, at_raw_ns })));
}
```

`modelled_consumer_never_emits_after_a_stop`. Against the modelled consumer (D-45): from any state
reached by an abort, there is no permit to hand it, so its emission count cannot move.
`ModelledConsumer::emit` takes an `OutputPermit` by value and there is no other way to call it, so
"cannot obtain a permit" and "cannot emit" are the same statement rather than two hopefully-equal
ones.

```rust
#[kani::proof]
fn modelled_consumer_never_emits_after_a_stop() {
    let state: State = kani::any();
    let cause: Cause = kani::any();
    let at_raw_ns: u64 = kani::any();
    let stopped_state = step(state, Event::Abort { cause, at_raw_ns });

    let before: u64 = kani::any();
    let consumer = ModelledConsumer::with_emitted(before);
    assert!(!would_issue_permit(stopped_state));
    assert!(consumer.emitted() == before);
}
```

Family 4, STOP-04, panic and overflow freedom. Kani checks for arithmetic overflow,
index-out-of-bounds and reachable panics automatically in every harness above; family 4 makes that
guarantee explicit at the one place in the crate where arithmetic happens at all.

```rust
#[kani::proof]
fn consumer_emit_never_overflows() {
    let before: u64 = kani::any();
    let mut consumer = ModelledConsumer::with_emitted(before);
    let permit = OutputPermit { _issued_by_the_gate: () };
    consumer.emit(permit);
    assert!(consumer.emitted() >= before);
}
```

A plain `+= 1` in `ModelledConsumer::emit` would panic here in a debug build and this harness
would fail; `saturating_add` is why it does not. Constructing the permit directly is allowed here
and only here: `crates/stop/src/proofs.rs` is inside the crate, so it reaches the `pub(crate)`
field. Do not add a public constructor to `OutputPermit` to make the harness easier to write.
T-2-09 in plan 02-02's threat model is exactly this, and a forged permit reachable from outside
the crate deletes STOP-03 while leaving every harness green.

Its skeleton:

```sh
#!/bin/sh
# Regenerates docs/proofs/emergency-stop-proof-report.md from a real cargo kani run (D-54).
#
# On demand, not on every CI run. D-54 asks for the report to be refreshed deliberately and
# reviewed like any published claim under D-07, and a file that rewrites itself on every push is
# neither deliberate nor reviewed. The report records the commit it was generated from so a
# reader can see whether it describes the tree in front of them.
#
# Usage: scripts/nr-proof-report.sh
set -eu

OUT=docs/proofs/emergency-stop-proof-report.md
RAW=$(mktemp -t nr-proof.XXXXXX)
trap 'rm -f "$RAW"' EXIT

KANI_VERSION=$(cargo kani --version)
SHA=$(git rev-parse HEAD)
DIRTY=clean
if [ -n "$(git status --porcelain)" ]; then DIRTY=dirty; fi

STATUS=0
START=$(date +%s)
cargo kani -p nr-stop > "$RAW" 2>&1 || STATUS=$?
ELAPSED=$(( $(date +%s) - START ))

# render $OUT from $RAW, $KANI_VERSION, $SHA, $DIRTY and $ELAPSED
# then:
exit "$STATUS"
```

The rendered report must contain, and a reader must be able to check each without running
anything:

  - A title and a one-paragraph statement of what the report is: the committed result of a solver
    run over `crates/stop`, and the evidence behind STOP-04.
  - The Kani version string, verbatim from `cargo kani --version`.
  - The commit the report was generated from, and whether the working tree was clean or dirty at
    the time. A dirty tree is recorded, not refused: a report that says it describes a modified
    tree is more useful than one that refuses to exist.
  - A table with one row per harness: harness name, the D-46 family it belongs to, the requirement
    it serves, and its outcome.
  - The total number of checks Kani reported and the number that succeeded.
  - The final verdict line verbatim.
  - The wall clock of the run.
  - A short section headed `What this report does not say`, pointing at
    `docs/proofs/emergency-stop-proof-scope.md` (which plan 02-05 writes) and stating in one
    sentence that the proof covers the sequential transition function and the gate predicate and
    covers no thread interleaving.
  - The exact command that regenerates it.

Two rendering rules. First, do not infer the harness-to-requirement mapping at render time by
parsing names: keep the mapping as an explicit table inside the script, so adding a harness
without classifying it produces an obviously incomplete row rather than a guess. Second, if
`cargo kani` reports any failure, the script must still render the report, with the failing rows
marked and the verdict line intact, and then exit non-zero. A generator that refuses to write a
report when the news is bad is a generator that only ever publishes good news.

Prose style is enforced in this repository and this file is published: no em dashes, ASCII only,
no emoji, sentence case headings. Match `docs/measurement-protocol.md`.

<threat_model>
## Trust boundaries

This plan produces the phase's central claim. Its real threats are about the claim being believed
when it is not earned. There is no network surface, no input and no secret here.

| Boundary | Description |
|----------|-------------|
| a solver run -> a published claim | The report asserts what was proved, and a reader will not re-run the solver. |
| a harness name -> a CI gate | Plan 02-04 proves the harnesses ran by grepping for these names. |
| the proved surface -> the unproved surface | `step` and `would_issue_permit` are proved; `latch.rs` is not, and the boundary between them must not blur. |

## STRIDE threat register

| Threat ID | Category | Component | Disposition | Mitigation plan |
|-----------|----------|-----------|-------------|-----------------|
| T-2-14 | Spoofing | a harness that passes vacuously | mitigate | Every harness asserts a property over `kani::any()` inputs rather than over chosen constants, and three of them use `kani::assume` to narrow rather than to define the answer. Plan 02-01 task 2 already established that this Kani build reports `VERIFICATION:- FAILED` when a statement is false, so a uniformly green result is not being taken on faith. |
| T-2-15 | Spoofing | `cargo kani` exiting 0 with zero harnesses found | mitigate | The harness names are fixed by this plan and recorded in the SUMMARY, and plan 02-04's `scripts/nr-proofs.sh` greps for each one by name before accepting the run. A rename or a `cfg` mistake that silently removes a harness fails the gate instead of passing it. |
