<objective>
Make the proof and the coverage bar blocking checks, and make both of them impossible to satisfy
without actually running.

Purpose. STOP-05 asks for `cargo kani` to pass in CI as a blocking gate. STOP-06 asks for 100
percent branch coverage of the module. Both are easy to write badly, and both failure modes are
worse than having no check at all, because a green check that proves nothing is trusted.

The two ways they go wrong here are specific and both are guarded against by name. `cargo kani`
exits 0 when it finds no harnesses at all, so a rename, a `cfg` mistake or a module that stopped
being declared produces a passing gate over an empty proof. And a coverage run that failed to
instrument a source file reports that file as absent rather than as zero, so any percentage
threshold passes vacuously. Neither is hypothetical; both are cheap to close, and closing them is
most of this plan.

The second thing this plan does is finish STOP-06 itself. Plan 02-02 wrote the crate against a
brief that kept the branch count small on purpose (D-32's single poll point, the small exhaustive
matches), so reaching 100 percent should be a matter of a small number of missing tests rather
than an exercise in writing tests for coverage's sake. If it is not, that is a finding about the
crate, and the honest response is to remove the unreachable branch rather than to write a test
that reaches nothing.

D-57 is honoured exactly: the pinned dated nightly applies to the coverage command alone, and
`rust-toolchain.toml` stays on stable. D-52 is honoured exactly: the Kani job is unconditional,
with the same trigger shape as `fmt`, `clippy`, `test` and `deny`, and no paths filter. A required
check that reports skipped on most pushes either blocks merges or silently stops guarding.

STOP-06 closes here, on the FSM, before any rig work begins. Running the rig work first would let
a coverage gap hide behind it.

Runs entirely on the macOS dev host, plus one real CI run to confirm the two new jobs pass on
`ubuntu-latest`. No rig.

Output: two new blocking jobs in `ci.yml`, two committed gate scripts, and `crates/stop` at 100
percent branch coverage.

Create `scripts/nr-proofs.sh`, mode 0755. This is the single definition of the proof gate, run
both by CI and by hand on the dev host, so the two cannot drift.

```sh
#!/bin/sh
# STOP-05: cargo kani over crates/stop, as a blocking gate (D-52).
#
# This script exists rather than a bare `cargo kani -p nr-stop` in the workflow because
# cargo kani exits 0 when it finds no harnesses at all. A rename, a cfg mistake, or a module
# that stopped being declared would then produce a green required check over an empty proof,
# which is worse than having no check: a gate nobody believes gets fixed, and a gate everybody
# believes and that guards nothing does not.
set -eu

# The harnesses crates/stop/src/proofs.rs is expected to contain, from plan 02-03. Adding a
# harness means adding it here too; that is deliberate friction on the one file that decides
# what "the proof passed" means.
EXPECTED='step_is_total
state_raw_round_trips
state_from_raw_is_total_and_fails_closed
cause_raw_round_trips_and_is_total
abort_never_returns_to_running
running_is_never_reachable_from_stopping_or_stopped
stopped_is_terminal
no_permit_when_not_running
permit_supply_closes_on_the_abort_edge
modelled_consumer_never_emits_after_a_stop
consumer_emit_never_overflows'

RAW=$(mktemp -t nr-proofs.XXXXXX)
trap 'rm -f "$RAW"' EXIT

STATUS=0
cargo kani -p nr-stop > "$RAW" 2>&1 || STATUS=$?
cat "$RAW"

if [ "$STATUS" -ne 0 ]; then
    echo "nr-proofs.sh: cargo kani exited $STATUS" >&2
    exit "$STATUS"
fi

if grep -q 'VERIFICATION:- FAILED' "$RAW"; then
    echo "nr-proofs.sh: at least one harness reported FAILED" >&2
    exit 1
fi

MISSING=0
for harness in $EXPECTED; do
    if ! grep -q "$harness" "$RAW"; then
        echo "nr-proofs.sh: expected harness $harness did not appear in the output" >&2
        MISSING=1
    fi
done
[ "$MISSING" -eq 0 ] || exit 1

EXPECTED_COUNT=$(printf '%s\n' "$EXPECTED" | wc -l | tr -d ' ')
SUCCEEDED=$(grep -c 'VERIFICATION:- SUCCESSFUL' "$RAW" || true)
if [ "$SUCCEEDED" -ne "$EXPECTED_COUNT" ]; then
    echo "nr-proofs.sh: expected $EXPECTED_COUNT successful verifications, saw $SUCCEEDED" >&2
    exit 1
fi

echo "nr-proofs.sh: $SUCCEEDED of $EXPECTED_COUNT harnesses verified"
```

line embeds the name in a longer string, grep for the name alone rather than reconstructing the

<threat_model>
## Trust boundaries

This plan turns two tools into required checks. Everything it guards against is a check that
appears to pass while proving nothing. There is no network input and no secret here; the closest
thing to a credential in scope is the existing rig push token, which this plan does not touch.

| Boundary | Description |
|----------|-------------|
| a CI job's exit status -> a merge decision | Both new checks are blocking, so their exit status is the whole signal a reviewer acts on. |
| a pinned tool version -> the guarantee the check represents | Kani's version and the nightly date both determine what was actually checked. |
| a committed script -> what runs in CI and what runs on the dev host | One definition each, so a green local run and a green CI run mean the same thing. |
