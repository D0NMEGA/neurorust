<objective>
Re-take D-18 with an instrument that can sample the isolated cores, and correct every published
figure that described one CPU as a machine-wide firmware floor.

Purpose: this repository currently contains four `hwlatdetect` captures from the 2026-08-28
screening and four from the installed PREEMPT_RT system, and not one of them names a CPU between
6 and 11. The 22 us figure that has been treated as the firmware floor comes from 13 events that
all named CPU 0. The three 2026-09-05 arms produced 32 events that all named CPU 5. Even the
untuned live-USB arm, whose scheduler was free to move the tracer thread anywhere, only ever
reached CPUs 2 and 4.

`rtla hwnoise -c 6-11 -H 0-5` runs one osnoise sampling thread per listed CPU, so a CPU absent
from its output was sampled and reported nothing rather than never being sampled. `rdmsr -p <cpu>
0x34` counts the system management interrupts that actually reached each CPU, exactly, over the
run. Between them the question D-18 has been asking since 2026-08-28 becomes answerable.

Two things this plan must not do. It must not subtract anything from anything: finding 1 stands
and `render_plat03_verdict` already reports the two figures side by side, attributed to their
source runs, stating they are not combined. And it must not quietly supersede the old figures:
the published documents that imply a machine-wide floor are corrected where they were published,
not left standing beside a newer document that disagrees with them.

The captures run on the Dell Precision 3591. An executor agent working from the macOS dev host
cannot perform task 1.

Output: three firmware screens taken with the working instrument, a corrected firmware record,
and a corrected 2026-08-28 README.
</objective>

**A pinned load generator, because `--cpu N` does not place workers.** Write this once and reuse
it for arms 2 and 3. One `stress-ng` process per logical CPU, each pinned individually with
`taskset -c`, so a CPU under `isolcpus` gets a worker only because it was placed there
explicitly:

```sh
# /tmp/nr-load.sh <first-cpu>-<last-cpu or list> <timeout-seconds>
#   e.g. /tmp/nr-load.sh 0-21 2400
#        /tmp/nr-load.sh 0-5,12-21 2400
cpus=$(python3 -c "
import sys
out=[]
for part in sys.argv[1].split(','):
    if '-' in part:
        a,b=part.split('-'); out += list(range(int(a),int(b)+1))
    else: out.append(int(part))
print(' '.join(map(str,out)))" "$1")
for c in $cpus; do
    taskset -c "$c" stress-ng --cpu 1 --cpu-method matrixprod --timeout "${2}s" &
done
echo "started $(echo "$cpus" | wc -w) pinned workers"
```

`--cpu-method matrixprod` matches the historical arms; changing it changes an experimental input.
Verify placement before starting any capture, and record the output:

```sh
mpstat -P ALL 2 3 | tail -30      # every listed CPU near 100 percent
ps -eLo pid,tid,psr,comm | grep stress-ng | awk '{print $3}' | sort -n | uniq -c
```

Every CPU in the list must appear. If CPUs 6 to 11 are missing, the pinning failed and the arm
is not worth taking; that is the same `isolcpus` trap in new clothes.

**Timeouts. The load outlives the capture, not the other way round.** Each arm is 60 s of thermal

```sh
pgrep -c stress-ng     # run this immediately after the capture returns; must be non-zero
```

Record that number in the arm's `--note`. The previous firmware arms failed this and nobody
