<objective>
Split run admission into the two questions it currently conflates, so a clean run can reach the
headline series and a bad result cannot be dropped by the classifier that exists to protect the
series from bad results.

Purpose: `config/contamination-thresholds.json` carries `"status": "provisional"`. In
`crates/cli/src/cmd/run.rs`, `determine_exclusion` returns `excluded_from_series = true`
unconditionally whenever `thresholds_provisional` is set. Every one of the D-18 re-take arms came
back excluded with that reason while every one of them was `Clean`. Plan 01-13 requires
`excluded_from_series = false` for the headline capture and plan 01-14's weekly comparison skips
excluded entries, so as the code stands the headline figure cannot be taken and the regression
series would be empty even once it exists.

The obvious fix is wrong. Flipping the status to `calibrated` would admit runs, but the D-24
classifier decides from the shape of the measured latency itself: `tail_excursion_ratio` is
`max / p99` and `thread_max_spread` is the relative spread of the per-thread maxima, both computed
in `compute_tail_metrics` from the run's own histogram. A genuine platform regression produces the
same signature as contamination (a rare excursion landing at nearly the same value on every
isolated thread is what a global stall looks like, and it is also what the D-17 contaminated arm
looked like), so a real bad result would be classified as contaminated and silently dropped from
the series that exists to catch it. The measurement would be deciding whether the measurement
counts.

There is also a bootstrap argument, and it was checked against the code before being relied on
here. `Thresholds::parse` accepts `calibrated` only when every `per_run_hour` value is set, and
`config/contamination-thresholds.json` leaves all five null with a recorded reason: the observed
magnitudes are implausible and two runs of unequal duration are not a calibration set. Calibrating
any threshold set needs a body of clean runs; a body of clean runs needs runs to be admitted;
so admission cannot depend on calibrated thresholds without a circular dependency. This is not a
temporary inconvenience to be waited out, it is a property of the design as written.

The split this plan implements:

  - **Was this run taken under the documented conditions?** Judged only from evidence causally
    upstream of, and independent of, the latency number: the precondition results, tool exit
    codes, fixture use, the precondition waiver, the `/proc/interrupts` counter deltas against
    calibrated thresholds when calibrated thresholds exist, the exact `MSR_SMI_COUNT` delta, and
    the recorded thermal maximum. This is the admission gate. Evidence of a cause excludes.
  - **Does this run's shape look like the global-stall signature?** That is D-24. It stays exactly
    where it is, in `interference.verdict` and `interference.tail_metrics`, is recorded on the
    manifest and rendered in the report, and never removes a run from the series by itself.

The invariant is enforced by the type signature rather than by discipline: `determine_admission`
is handed an `InterferenceDelta` and an `Option<&CalibratedThresholds>`, never the
`InterferenceSnapshotPair` and never `TailMetrics`, so it cannot consult the verdict or the tail
metrics even by mistake. A future edit that wants to would have to change the signature, which is
visible in review.

Runs entirely on the macOS dev host. No rig access, no captures taken.

Output: a two-verdict manifest record, an admission gate that cannot see the number, and every
published description of the old behaviour corrected.

/// Why this run is, or is not, admitted to the headline regression series.
///
/// Decided **only** from evidence causally upstream of the latency number this run measured:
/// the precondition results, tool exit codes, fixture use, the precondition waiver, the
/// `/proc/interrupts` counter deltas against calibrated thresholds when calibrated thresholds
/// exist, the exact `MSR_SMI_COUNT` delta, and the recorded thermal maximum.
///
/// It is deliberately NOT decided from `InterferenceSnapshotPair::verdict` or from
/// `TailMetrics`. Those are an inference from the effect: `tail_excursion_ratio` is
/// `max / p99` and `thread_max_spread` is the relative spread of the per-thread maxima, both
/// computed from this run's own histogram. A genuine platform regression produces the same
/// signature as contamination, so admitting on that signal would silently drop the exact
/// results the regression series exists to catch. See `01-REVIEW-2026-09-06.md` finding A1 and
/// decision D-28.
///
/// The D-24 shape verdict is still computed, still recorded in
/// [`RunManifest::interference`], and still rendered in `REPORT.md`. It annotates; it does not

pub struct SeriesAdmission {

    pub admitted: bool,
    /// One entry per upstream evidence source that excluded this run, each naming the evidence
    /// and its observed value. Empty if and only if `admitted` is true.
    pub exclusions: Vec<String>,
    /// Every upstream evidence source the gate consulted, with what it observed and what it
    /// made of it, whether or not it excluded. A source that could not be evaluated says so
    /// rather than being omitted, for the same reason a precondition that could not be read is
    /// recorded `unavailable` rather than dropped (D-06).
    pub evidence: Vec<AdmissionEvidence>,
}

    /// e.g. `15 pass, 0 fail, 0 unavailable` or `cal max 6, tlb max 6, res max 55, irq max 1127
    /// over 3600s`.

    pub disposition: AdmissionDisposition,

The gate builds one `AdmissionEvidence` entry per source, in this fixed order, and appends the
text of every `Excluding` entry to `exclusions` in the same order:

  1. `PreconditionWaiver`. `Some(reason)` gives `Excluding` carrying
     `precondition_waiver_reason`'s existing text verbatim; `None` gives `Clean` with observed
     `not given`. D-17 makes this unconditional and it stays unconditional.
  2. `FixtureUse`. A non-empty `fixtures_used` gives `Excluding` carrying
     `fixture_usage_reason`'s existing text verbatim; empty gives `Clean` with observed `none`.
  3. `ToolExitCodes`. Reuse `is_tool_failure` unchanged, so `hwlatdetect` exit 1 stays a finding
     rather than a failure. Observed is every tool name with its exit code, e.g.
     `cyclictest=0 rtla=0`.
  4. `Preconditions`. `Excluding` when any result is `Fail`, or when any result is `Unavailable`
     and `instrument_class` is `HeadlineSeries`. This mirrors `refuse_on_violation` exactly; the
     gate records the basis even though a run normally never reaches here with a violation,
     because a waived run must show what was waived. The exclusion text names each offending
     check with its `observed` and `expected`. Observed is the tally,
     e.g. `15 pass, 0 fail, 0 not-applicable, 0 unavailable`.
  5. `InterferenceCounters`. With `Some(limits)`, call `interference::counter_breach`; a breach
     gives `Excluding` with its reason. With `None`, give `NotThresholded`. Observed in both
     cases is the maximum per-CPU delta of each of the four counters and the run duration, e.g.
     `cal max 6 on cpu9, tlb max 6 on cpu6, res max 55 on cpu7, irq max 1127 on cpu6, over
     3600s`.
  6. `SmiDelta`. `Unavailable` when `smi.unavailable_reason` is `Some`, carrying that reason.
     Otherwise `NotThresholded`, observed as the per-CPU deltas, e.g. `cpu6=0 cpu7=0 ...`. No
     calibrated SMI ceiling exists, so this never excludes. Say that in a comment, so the next

<threat_model>
## Trust boundaries

| Boundary | Description |
|----------|-------------|
| a measured latency -> a decision about whether that measurement counts | The circularity finding A1 names. Crossing it lets the instrument suppress its own bad news. |
| an operator flag (`--allow-precondition-violation`) -> the published series | A flag that waives the assertion list must never also waive exclusion. |
| a manifest summary field -> the record it summarises | `excluded_from_series` and `exclusion_reason` are what every consumer reads; if they can drift from `series_admission`, the record is decorative. |

## STRIDE threat register

| Threat ID | Category | Component | Disposition | Mitigation plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-107 | Repudiation | crates/cli/src/cmd/run.rs, determine_admission | mitigate | The gate is handed `InterferenceDelta` and `Option<&CalibratedThresholds>` and is never handed `InterferenceSnapshotPair`, `ContaminationVerdict` or `TailMetrics`. A future edit that wants to exclude on the measured shape must widen `AdmissionInputs`, which is a visible diff. A test asserts the struct names none of those three types. |
| T-1-108 | Tampering | the headline regression series | mitigate | A genuine platform regression has the same tail signature as contamination, so admitting on that signal would silently drop the results the series exists to catch. The gate excludes only on evidence of a cause, and a run excluded that way carries the evidence text in `exclusions`, so a suppressed run is always attributable to a named observation rather than to a classifier. |
| T-1-109 | Elevation of privilege | --allow-precondition-violation | mitigate | The waiver becomes evidence source 1 and stays unconditional: `Some(reason)` always produces `Excluding` with `precondition_waiver_reason`'s existing text. The three existing tests that pin this behaviour must pass unchanged, and the task text forbids weakening them. |
| T-1-110 | Repudiation | RunManifest.excluded_from_series | mitigate | `validate` refuses any manifest where `series_admission.admitted != !excluded_from_series`, or where an admitted run carries exclusions. The summary and the record cannot disagree, so a hand-edited manifest that flips one without the other fails the blocking D-13 gate. |
| T-1-111 | Repudiation | published descriptions of the gate | mitigate | Four source doc comments, three documents and one config note currently describe the removed behaviour. Task 3 corrects all eight by name and then greps for the ones this plan did not anticipate, with the grep in the task's own verify command. A stale description of a security-relevant gate is how the next reader reasons wrongly about it. |
| T-1-112 | Spoofing | an unavailable precondition on a headline run | mitigate | `Unavailable` excludes a `headline-series` run exactly as `refuse_on_violation` already refuses one, so a check that could not be evaluated is never counted as a pass by the admission gate either. An `investigation` run may proceed, since it never feeds the series. |
