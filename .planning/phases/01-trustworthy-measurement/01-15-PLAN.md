Two halves: the credential, then the deployment.

**Create the token.** In the GitHub web interface, under Settings, Developer settings,
Personal access tokens, Fine-grained tokens:

  - Resource owner: the account that owns this repository
  - Repository access: Only select repositories, and select this repository alone
  - Permissions: Contents, Read and write. Nothing else. Do not grant Actions, Workflows,
    Administration, Secrets or Metadata beyond what is auto-required
  - Expiration: 90 days

Do not use a classic personal access token. A classic token cannot be scoped to a single
repository, so a lost laptop would expose every repository the account can reach. That is threat
T-1-01 and the fine-grained token is the whole mitigation.

Write the expiry date into `deploy/systemd/README.md` under a heading "Credential rotation", with
the date the token must be replaced and a one-line procedure. A credential that silently expires
turns into eight weeks of coverage gaps before anyone notices.

**Install the credential on the rig:**

```sh
sudo mkdir -p /etc/neurorust
printf '%s' '<the token>' | sudo tee /etc/neurorust/push-token > /dev/null
sudo chown root:root /etc/neurorust/push-token
sudo chmod 0600 /etc/neurorust/push-token
sudo chmod 0700 /etc/neurorust
# Confirm, and confirm the token is not in your shell history
sudo ls -l /etc/neurorust/push-token
history -d $((HISTCMD-4)) 2>/dev/null || true
```

Use `printf '%s'` rather than `echo` so no trailing newline is written; a trailing newline in the
token file breaks the credential helper in a way that produces an unhelpful authentication error.

**Deploy the repository:**

```sh
sudo git clone https://github.com/<owner>/neurorust.git /opt/neurorust
cd /opt/neurorust
sudo git config --global --add safe.directory /opt/neurorust
sudo cargo build -p nr-cli --release
sudo /opt/neurorust/target/release/nrmeasure --version
```

The service runs as root with `WorkingDirectory=/opt/neurorust`, so the checkout must be
root-owned and the build must produce the binary at the path the unit's `ConditionPathExists`
names. Confirm both before continuing:

```sh
ls -l /opt/neurorust/target/release/nrmeasure
sudo -u root git -C /opt/neurorust status --short
```

Note that `/opt/neurorust` is a second checkout, separate from the one used for the manual runs in
plans 01-11 through 01-13. That is deliberate: the unattended job should not compete with an
interactive working tree, and a dirty interactive tree would otherwise end up in the manifest's
`harness.git_dirty` flag on an unattended run.

<threat_model>
## Trust boundaries

| Boundary | Description |
|----------|-------------|
| the rig -> the public repository | An unattended process on a personal laptop can write to a public repository every week |
| the GitHub UI -> the token scope | The scope chosen at creation time is the only thing bounding what a stolen token can do |
| the timer -> an unattended measurement | Nobody is watching when this runs, so every safety property has to hold without a human |

## STRIDE threat register

| Threat ID | Category | Component | Disposition | Mitigation plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-01 | Elevation of privilege | /etc/neurorust/push-token, the GitHub token | mitigate | Fine-grained token, resource owner set to the repository owner, repository access limited to this one repository, permissions limited to Contents read and write, with a 90 day expiry recorded in `deploy/systemd/README.md`. Stored root-owned at mode 0600 in a 0700 directory, written with `printf '%s'` so no trailing newline, read through a git credential helper so it never enters the environment, the journal or the process list. A classic token is explicitly rejected because it cannot be scoped to one repository. |
| T-1-42 | Elevation of privilege | the rig checkout at /opt/neurorust | mitigate | The unattended job runs from a separate root-owned checkout, not from the operator's interactive working tree. An interactive tree with uncommitted changes would otherwise be what the service builds and measures from, and `harness.git_dirty` would be set on published runs. |
| T-1-40 | Tampering | the unattended push | mitigate | Verified in task 2 by inspection of the rig's own commit: it must add only `measurements/`, `metrics/latency-series.json`, `metrics/coverage.json` and `measurements/INDEX.md`, and must change nothing under `docs/` and nothing in `metrics/baseline.json`. The unattended path therefore cannot alter a published claim or move the baseline. |
| T-1-43 | Tampering | making the scheduled run pass | mitigate | An acceptance criterion forbids weakening any precondition to make the scheduled run green. If the machine defaults to `graphical.target`, the correct responses are to change the machine's default or to accept recorded coverage gaps, not to relax the assertion. |
| T-1-44 | Repudiation | a silently missing week | mitigate | Task 3 requires the most recent ISO week to be present in `metrics/coverage.json` as either a run or a gap with a reason. A week that is simply absent is treated as a defect in the wrapper's refusal path rather than as a normal outcome, which is what stops D-08's gap record from quietly degrading into a hole. |
| T-1-45 | Information disclosure | journalctl output pasted into an issue or a commit | accept | The journal for a run contains the full tool argument vectors including output paths under `/opt/neurorust`. Accepted: those paths carry no credential and no host identifier beyond what the manifest already publishes. Do not paste journal output containing the credential helper invocation. |
</threat_model>
