<objective>
Root-cause the stall, within a fixed budget, and publish whatever the answer turns out to be.

Purpose: PLAT-01 says the 3.8 ms global stall observed on the RT kernel is root-caused with
ftrace and `cyclictest --tracemark`, and the responsible kernel path is named. D-19 defines
"named" as a specific kernel path identified from that capture, with the capture committed next
to the claim, one named path per distinct phenomenon. D-20 budgets three capture and analyse
cycles, after which what is known is published as a documented open question and work proceeds to
Phase 2. D-21 says that if the stall does not reproduce on a clean run, that is the result.

**What D-21 does not say, and what governs instead.** D-21's own wording proposes closing PLAT-01
with "the 3.8 ms stall was an artifact of measurement contamination". ROADMAP success criterion 1,
rewritten on 2026-09-07, supersedes that: non-reproduction is not a cause and may not be recorded
as one. A clean run that does not show the stall establishes that it was not observed under those
conditions, over that exposure. It does not exclude the kernel, it does not establish
contamination as the mechanism, and it does not by itself bound how often the stall occurs, since
a frequency bound needs assumptions about the event's distribution that nothing in this
investigation supplies. The non-reproduction branch of task 3 is written to commit exactly what
criterion 1 requires and nothing beyond it: the protocol, the total exposure, what that exposure
does and does not bound, PLAT-01 left open, and the stall carried as an explicit limitation on
every published latency figure. The three-cycle budget is unchanged.

Three things make this more than "run cyclictest with tracing on", and one of them is new since
this plan was first written.

**The tracing has to be armed, and the arming has to be verified.** The earlier version of this
plan said `--breaktrace` "also passes `--tracemark`, which arms ftrace". It does not. Those flags
write a marker and stop tracing when a threshold is breached; they do not select or enable a
diagnostic event set. A capture cycle taken with `current_tracer` at `nop` and no events enabled
produces a stopped, empty buffer and costs an hour. External audit finding 9. So the event set is
configured explicitly and a short trial confirms the buffer actually holds those events, on CPUs
6 to 11, before any real cycle is spent.

**The threshold has to be calibrated against a traced baseline.** Enabling tracing inflates
system latency, so a threshold derived from an untraced run either never fires or fires on
tracing overhead. The Linux Foundation RT wiki's worked example goes from a 130 us untraced
maximum to a 190 us traced maximum, making the real break limit 180 and not 130.

**There are two phenomena and one threshold cannot catch both.** The 2026-08-28 capture shows
roughly 140 overflows per thread clustered inside cycles 1,820,584 to 1,826,674, about 1.2
seconds of wall time carrying a stall over 400 us roughly every 10 ms on every isolated core at
once. Separately there are a handful of isolated cross-thread events near cycles 2,259,348,
2,349,428 and 2,709,344. A break limit tuned to a multi-millisecond spike never fires on a 400 us
burst.

**What is different now.** Plan 01-11 took the D-17 calibration pair and it points hard at D-21.
The clean 3600 s arm's maximum was 78 us. The contaminated 900 s arm reached 3856 us and the
duration-matched contaminated arm reached 1901 us. The roughly 3.8 ms stall reproduced under
contamination and did not appear on the clean arm. That is not proof, and this plan does not
assume it: it is the reason cycle 1 is worth spending on instrument calibration rather than on
chasing an event that may not occur under the protocol.

This plan runs on the Dell Precision 3591. An executor agent working from the macOS dev host
cannot perform tasks 1 or 2.

Output: up to three investigation run directories, one published investigation document stating
which outcome occurred, and one correction to a published attribution the captures cannot
support.

**Step 1, choose the event set from what this kernel actually has.** Do not copy an event list
from anywhere, including from this plan, without checking it:

```sh
grep -E '^(sched|irq|ipi|timer|workqueue|tlb):' /sys/kernel/tracing/available_events | sort
```

The candidates worth arming, each because it distinguishes a specific hypothesis:

    sched:sched_switch              which task displaced the cyclictest thread
    sched:sched_wakeup              whether the wakeup itself was late
    irq:irq_handler_entry           an interrupt reached an isolated core
    irq:irq_handler_exit            and how long it took
    timer:hrtimer_expire_entry      the tick, if the 10 ms spacing of phenomenon A is a tick
    workqueue:workqueue_execute_start  deferred work landing on an isolated core
    ipi:ipi_send_cpu                who sent an IPI to an isolated core, if the group exists
    tlb:tlb_flush                   a system-wide TLB shootdown, one of the two named suspects

Keep only the ones `available_events` lists. Record the final set verbatim; it is an
experimental input and it goes in the manifest note and in the write-up.

**Step 2, arm tracing and prove the buffer holds it.** This step exists because the previous
version of this plan assumed `--tracemark` did it:

```sh
T=/sys/kernel/tracing
```
