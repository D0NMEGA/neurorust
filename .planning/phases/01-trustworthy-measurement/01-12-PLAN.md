<objective>
Root-cause the stall, within a fixed budget, and publish whatever the answer turns out to be.

Purpose: PLAT-01 says the 3.8 ms global stall observed on the RT kernel is root-caused with
ftrace and `cyclictest --tracemark`, and the responsible kernel path is named. D-19 defines
"named" as a specific kernel path identified from that capture, with the capture committed next
to the claim, one named path per distinct phenomenon. D-20 budgets the investigation at three
capture and analyse cycles, after which what is known is published as a documented open question
and work proceeds to Phase 2. D-21 says that if the stall does not reproduce on a clean run, that
is the result, not a failure.

Two things make this plan more than "run cyclictest with tracing on".

First, the break-trace threshold must be calibrated against a traced baseline. Enabling ftrace
inflates system latency, so a threshold derived from an untraced run either never fires or fires
constantly on tracing overhead. The Linux Foundation RT wiki's worked example goes from a 130 us
untraced maximum to a 190 us traced maximum, so the real break limit becomes 180 us and not 130.
That calibration is task 1 and it consumes part of the three-cycle budget.

Second, there are two phenomena and one threshold cannot catch both. The 2026-08-28 capture shows
roughly 140 overflows per thread clustered inside cycles 1,820,584 to 1,826,674, which at a 200 us
interval is about 1.2 seconds of wall time carrying a stall over 400 us roughly every 10 ms on
every isolated core at once. Separately there are a handful of isolated cross-thread events near
cycles 2,259,348, 2,349,428 and 2,709,344, and the roughly 3.8 ms maximum belongs to that second
category. A break limit tuned to the 3.8 ms spike will never fire on the 400 us burst.

This plan runs on the Dell Precision 3591. An executor agent working from the macOS dev host
cannot perform any task in it. Every capture task below is a runbook.

Output: up to three investigation run directories and one published investigation document
stating which of the three defined outcomes occurred.
</objective>

## Trust boundaries

| Boundary | Description |
|----------|-------------|
| investigation runs -> the headline series | Tracer overhead inflates every number in an investigation run; one leaking into the series contaminates the thing this phase exists to make trustworthy |
| a trace -> a named kernel path | Reading a stack trace is human inference, and an overconfident reading published as a finding is worse than an open question |
| the three-cycle budget -> Phase 2 | An unbounded investigation delays the project's most differentiating artifact |
