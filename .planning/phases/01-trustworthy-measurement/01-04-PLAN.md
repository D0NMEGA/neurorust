Write `crates/histogram/src/hist.rs` parsing the exact format documented in
`crates/histogram/tests/fixtures/README.md`. Restating it here so the action is self-contained:

  Line 1 is the literal `# Histogram`.
  Data lines are `%06d` bin index then one `%06d` count per column. The first separator is a
  space and the rest are tabs, so split on any whitespace.
  Bin index is latency in microseconds at 1 us resolution.
  Footer lines, in order:
    `# Min Latencies: <n per thread>`
    `# Avg Latencies: <n per thread>`
    `# Max Latencies: <n per thread>`
    `# Histogram Overflows: <n per thread>`
    `# Histogram Overflow at cycle number:`
    `# Thread <i>: <space separated cycle numbers>` (one line per thread)

Column count rule, confirmed on the rig by plan 01-02: `-h/--histogram` writes one column per
thread. `-H/--histofall` writes one column per thread plus one summary column on the right. The
number of threads is authoritative from the `# Max Latencies:` footer line, which always has
exactly one value per thread. Parse the footer first, take the thread count from it, then decide
whether the data lines have `threads` or `threads + 1` columns. If they have `threads + 1`,
record `summary_column_present: true` and DROP the last column; do not add it to any total. If
they have neither count, return `HistError::ColumnCountMismatch { expected, found }`.

This is the single most likely place to silently double the sample count, which is why
`histofall_summary_column_not_double_counted` is a required test.

Public type:

```rust
pub struct CyclictestRun {
    pub threads: usize,
    pub summary_column_present: bool,
    pub bins: BTreeMap<u64, Vec<u64>>,      // bin_us -> per-thread counts, threads long
    pub min_us: Vec<u64>,                   // per thread
    pub avg_us: Vec<u64>,                   // per thread, as cyclictest reported it (integer)
    pub max_us: Vec<u64>,                   // per thread
    pub overflows: Vec<u64>,                // per thread
    pub overflow_cycles: Vec<Vec<u64>>,     // per thread
    pub overflow_bound_us: u64,
    pub overflow_bound_source: OverflowBoundSource,
}

pub enum OverflowBoundSource {
    Declared,   // the caller passed the --histogram / --histofall value
    Derived,    // computed as highest present bin + 1
}
```

Build one `hdrhistogram::Histogram<u64>` per thread with 3 significant figures

record the overflows:

```rust
// cyclictest reports overflows separately from the bins. They are samples at or above the
// histogram bound and they must be recorded, or every percentile, every over-gate count and
// every total is wrong. This is the exact error corrected under D-23.
for _ in 0..run.overflows[thread] {

```

State the convention in the module doc comment in these words or equivalent: "Overflow samples
are recorded at the histogram bound, which is a lower bound on their true value. Percentiles at
or above the overflow fraction are therefore conservative: the reported value is no larger than
the truth. The reported maximum comes from the cyclictest footer and is exact." RESEARCH.md
requires this convention to be stated because it makes high percentiles conservative and a
reader deserves to know.

Public surface:

```rust
pub struct Percentiles {
    pub total_samples: u64,          // binned + overflows
    pub binned_samples: u64,
    pub overflow_samples: u64,
    pub values: Vec<(f64, u64)>,     // (quantile, value_us), in the order requested
    pub max_us: u64,                 // from the footer, exact
    pub min_us: u64,
}

impl CyclictestRun {
    /// Percentiles over every sample, overflows included at the histogram bound.
    /// This is the correct computation and the only one used by nr-metrics.
    pub fn percentiles(&self, quantiles: &[f64]) -> Result<Percentiles, PercentileError>;

    /// Percentiles over binned samples only, ignoring the separately reported overflows.
    /// Present so tests can reproduce the figure the 2026-08-28 README published, and so the
    /// D-23 correction can show both numbers side by side. Do not use it for a new figure.
    pub fn percentiles_excluding_overflows(&self, quantiles: &[f64]) -> Result<Percentiles, PercentileError>;

    /// Count of samples strictly above `gate_us`, overflows included.
    pub fn samples_above(&self, gate_us: u64) -> u64;

    /// Count of samples strictly above `gate_us`, overflows excluded. Same caveat as above.
    pub fn samples_above_excluding_overflows(&self, gate_us: u64) -> u64;

    pub fn max_us(&self) -> u64;     // max over the per-thread footer maxima
    pub fn to_bin_table(&self) -> Vec<(u64, u64)>;   // bin_us, summed count across threads
}
```

The naming is deliberate: the correct method has the short name and the incorrect one has a long
explicit name with a doc comment saying not to use it for a new figure. That is the smallest
mechanism that stops the 2026-08-28 error recurring by accident.

<threat_model>
## Trust boundaries

| Boundary | Description |
|----------|-------------|
| cyclictest output file -> the parser | A capture file is untrusted input; it may be truncated, hand-edited, or from a different run |
| published percentile -> a reader | Every number this crate produces is a claim the project stakes its credibility on |

## STRIDE threat register

| Threat ID | Category | Component | Disposition | Mitigation plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-17 | Tampering | hist.rs, json.rs | mitigate | ASVS V5: reject rather than coerce. Ragged lines, a column count matching neither `threads` nor `threads + 1`, a missing footer line, and an overflow cycle list whose length disagrees with the declared overflow count all return a named error. `deny_unknown_fields` on the JSON type fails on a schema change instead of silently dropping data. `reconcile()` fails when a `.json` and a `.hist` from different runs are paired. |
| T-1-18 | Repudiation | percentiles.rs | mitigate | The incorrect (overflow-excluding) computation is reachable only through `percentiles_excluding_overflows` and `samples_above_excluding_overflows`, both documented as not for new figures. The default path counts overflows. A regression test seeded with the real 2026-08-28 capture asserts the exact corrected values, so the error cannot be reintroduced silently. |
| T-1-19 | Denial of service | hist.rs | accept | A hostile .hist file could declare a very large bin index and drive memory use. Accepted: the input is a file the operator produced on their own rig, there is no untrusted submission path, and the parser is an offline tool. Bounded in practice because bins come from a `BTreeMap` keyed by observed values rather than a preallocated array. |
</threat_model>
