  # Measurement protocol

  ## What this document is
  One paragraph: this is the state a machine must be in before a figure taken on it is
  publishable, and the exact commands that produce a run. State that the harness asserts every
  condition below and refuses to run when one is violated, and that it changes nothing about the
  system, so the operator brings the machine to this state themselves.

  ## Why it exists
  Cite the concrete failure it prevents, with the numbers from the 2026-08-28 README: SSH
  commands executed during a 10 minute run created processes, took network interrupts and
  triggered TLB shootdown IPIs that broadcast to the isolated cores, and /proc/interrupts showed
  CAL counts of roughly 137,000 on CPUs 6 to 11. A GNOME session was active with a user typing
  into it. That run produced a 2 us median and a 3.8 ms maximum, and neither number is
  publishable. Naming the specific failure is what makes the protocol credible rather than
  ceremonial.

  ## Required system state
  A table with one row per precondition check, four columns: check, required state, how to set
  it, how the harness observes it. All 14 rows, using the exact `PreconditionCheck` variant name
  in the first column so the consistency test can match on it. Fill "required state" and "how the
  harness observes it" from `crates/capture/src/preconditions.rs`, not from memory. "How to set
  it" is the operator's instruction, for example:

      SystemdDefaultTargetIsMultiUser    sudo systemctl isolate multi-user.target
      DisplayManagerInactive             sudo systemctl stop gdm.service
      GovernorIsPerformanceOnAllCpus     handled by rt-tuning.service on the reference rig
      NoPackageManagerActivity           sudo systemctl stop unattended-upgrades.service
      TracersQuiescent                   echo nop | sudo tee /sys/kernel/tracing/current_tracer

  ## Running a measurement
  The exact command sequence, in order:

    1. Check the environment without measuring:
         nrmeasure run --rig-slug <slug> --class headline --cpus 6-11 --main-cpus 0,1 \
                       --duration 14400 --dry-run
       This prints every assertion result and the exact tool command lines, and writes nothing.
       Fix anything it reports before continuing.
    2. Disconnect. Close every SSH session and every terminal on the machine. The run executes
       from a systemd oneshot service with no login session (see deploy/systemd, plan 01-14),
       which is what makes "no remote shell activity during a run" true by construction rather
       than by discipline.
    3. Take the run. State the two Phase 1 standard invocations verbatim: the weekly regression
       run (1 hour, class weekly, with hwlatdetect) and the headline run (4 hours, class
       headline). Give the full command line for each.
    4. Bring back the run directory and commit it. State that `nrmeasure verify --strict
       --check-index` must pass before the commit, and that CI runs the same check.

  ## What invalidates a run
  A list, each item with its consequence:
    - any of the 14 assertions failing: the harness refuses and writes nothing, and the week is
      recorded as a coverage gap rather than backfilled
    - a login session opened during the run: the interference counters will show it and the
      contamination verdict marks the run, which is retained and published but excluded from the
      headline series
    - a tracer armed during a headline-class run: refused, because tracer overhead inflates the
      numbers being published
    - running two measurement tools at once: they measure each other; the harness runs cyclictest
      and hwlatdetect in sequence, never concurrently

  ## Run classes and cadence
  State the classes and what each is for, and the cadence fixed in D-10: a roughly 1 hour weekly
  run for the regression series, plus a longer soak monthly or on demand before a published
  claim. State that a weekly 24 hour soak was rejected because the rig is also a Windows machine,
  because a reader deserves to know the constraint rather than wondering why the cadence is what
  it is. Reference OSADL's published practice (5 hours 33 minutes twice daily since 2011, 1 us
  resolution, worst case as the headline) as the reference this protocol is a smaller version of,
  and state the difference honestly rather than implying parity.

  ## The two-instrument rule
  Headline-series runs use cyclictest alone plus /proc/interrupts diffing, which has no
  measurement overhead. Investigation runs additionally use the timerlat or osnoise tracers,
  which run their own per-CPU threads and inflate the numbers. The two are tagged distinctly in
  the manifest by `instrument_class` and are never averaged together. An investigation run never
  feeds the regression series.

  ## Reproducing on different hardware
  One short section: what a third party must change (the CPU list, the isolcpus setting, the rig
  slug) and what they must not change (the interval, the histogram bound, the run duration for a
  comparable figure). State plainly that a figure from different hardware is a different figure
  and that the manifest records which machine it came from.

  # Publication layout

  ## Directory layout
  `measurements/<YYYY-MM-DD>-<rig-slug>-<run-class>[-NN]/`, with the date being the UTC run
  start, the class being one of the eight run classes, and `-NN` appended from the second run of
  the same date, rig and class onward starting at `-02`. State that
  `measurements/2026-08-28-precision3591/` keeps its pre-convention name because renaming it
  would break the links in PROJECT.md and REQUIREMENTS.md, and that it carries a reconstructed
  manifest instead.

  ## What a run directory contains
  `manifest.json` (the source of truth), `REPORT.md` (generated, never hand-edited), `hist.tsv`
  (derived, so a reader can plot without a Rust toolchain), and the raw captures byte-identical
  to what the tool emitted. State that the raw captures are never rewritten to embed provenance
  headers, and that the sidecar manifest exists precisely so they stay byte-identical.

  ## Raw captures: in the repository or behind a pointer
  In the repository by default. The stated thresholds, matching `crates/cli/src/rundir.rs`
  exactly: 25 MiB per file and 100 MiB per run directory. A cyclictest histogram from a 1 hour
  run is a few tens of kilobytes and hwlatdetect output is smaller, so those are always
  committed. The threshold exists for ftrace and trace-cmd captures from a PLAT-01 investigation.
  A file over the limit is compressed with `zstd -19` first, and only if it is still over the
  limit is it recorded as an external pointer with its blake3 still in the manifest, so the
  pointer remains verifiable.

  ## Histograms
  Generated on demand from the raw capture. No rendered images are committed. The in-repository
  visual form is the ASCII histogram in the generated `REPORT.md`, on a logarithmic count axis at
  1 us resolution, plus `hist.tsv` for anyone who wants to plot it themselves. State the reason:
  an ASCII histogram diffs cleanly in review and a PNG does not, and BENCH-05 asks for histograms
  rather than means, not for a particular image format.

  ## Losing configurations
  This is how BENCH-06 is operationalised. State the rules as rules:
    - No run directory is ever deleted, and no run is ever omitted from `measurements/INDEX.md`.
    - A run kept out of the headline series carries `excluded_from_series: true` and a non-empty
      `exclusion_reason` in its manifest, and the manifest fails validation without the reason.
    - `INDEX.md` has one row per run directory with its verdict, its p99, its maximum, whether it
      is in the series, and the exclusion reason when it is not.
    - `INDEX.md` is generated, and CI checks it against the generated form rather than
      regenerating it, so removing a row by hand fails the build.
    - The deliberately contaminated arm of the D-17 calibration pair is a published result, not a
      discarded one: it documents what contamination looks like, which is what a third party
      needs in order to avoid it.

  ## What a checksum proves
  Repeat the wording from `crates/manifest/src/checksum.rs`: blake3 checksums prove integrity,
  not authenticity. They detect accidental corruption and prove a capture matches its manifest.
  They do not prove who produced the capture. There is no signing story in v1. State this
  plainly rather than letting a reader infer more from the presence of hashes than they support.

  ## Where captures may live
  The two exempt trees and why each exists, matching `crates/cli/src/cmd/verify.rs`:
    - `crates/*/tests/fixtures/` holds parser fixtures. They are inputs to tests, not figures.
    - `docs/rig/recon-*/` holds schema probes from a rig recon session, all prefixed `probe-`.
      They pin down output formats and no number from them is ever published.
  State that the provenance gate scans the whole tracked tree by file shape, so a figure moved
  out of `measurements/` fails the build, and that this is deliberate.

  ## The metrics series
  `metrics/latency-series.json` (append only, auto-committed by the rig),
  `metrics/baseline.json` (the reviewed comparison baseline, changed only by a human in a
  reviewed commit), `metrics/coverage.json` (one entry per ISO week, a run reference or a gap
  with a reason). State D-07's split: the weekly p50, p95 and p99 JSON is a regression-tracking
  artifact and auto-commits, while anything that becomes a published claim reaches main only
  through a reviewed commit.

  ## Provenance tiers
  `harness-generated` and `reconstructed`, what each means, and how a reader tells them apart at
  a glance. State that a reconstructed manifest records every unrecorded field as explicitly
  absent with a reason, and never guesses one.

Do not restate the numbers from any measurement in this document. It describes the container, not
the contents. The one exception is the size thresholds, which are policy.

<threat_model>
## Trust boundaries

| Boundary | Description |
|----------|-------------|
| the protocol document -> a third party | A reader acts on this document; an omission becomes their contaminated run |
| the documentation -> a reader's inference | What the documentation implies about provenance strength is a claim the project makes |

## STRIDE threat register

| Threat ID | Category | Component | Disposition | Mitigation plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-07 | Spoofing | docs/publication-layout.md | mitigate | The "What a checksum proves" section states in public that blake3 checksums prove integrity and not authenticity, and that there is no signing story in v1. This is disclosure as mitigation: the risk is a reader inferring provenance strength the artifacts do not support, and the fix is saying so where they will read it. |
| T-1-29 | Repudiation | docs/measurement-protocol.md | mitigate | The protocol document and the harness assertion list are kept in sync by `protocol_doc.rs`, which fails when a check exists in code but not in the document or the reverse. A protocol that silently drifts from the tool is worse than none, because a third party following it would believe they had reproduced conditions they had not. |
| T-1-05 | Tampering | docs/publication-layout.md "Where captures may live" | mitigate | The prose states the same two exempt trees the CI gate enforces, so the rule is reviewable by a human as well as machine-checked. A future widening of the exemption is then visible as a documentation diff as well as a code diff. |
| T-1-30 | Information disclosure | docs/measurement-protocol.md | accept | The protocol document describes the reference rig's tuning in enough detail to identify the machine class. Accepted: the rig-discipline constraint requires naming the machine every figure was taken on, so this is the intended disclosure, and it carries no credential or host identifier. |
</threat_model>
