Build the metrics crate: the BENCH-08 series, the D-11 baseline comparison, the D-08 coverage
record, the BENCH-06 index, and the D-22 PLAT-03 decomposition.

Purpose: BENCH-08 asks for a weekly committed JSON carrying p50, p95 and p99 for every stage
instrumented so far. D-04 says that schema must generalise beyond cyclictest now, because
STOP-07 in Phase 2 and SUBS-06 in Phase 3 are its next writers, so the entry is keyed by a stage
name rather than shaped around cyclictest. D-11 puts the regression judgement in reviewable
configuration rather than in a script on the rig. D-08 says a missed week is a recorded gap, not
a backfill. BENCH-06 says losing configurations appear rather than being omitted, which here
means a contaminated or regressed run is rendered in the index with its reason, not filtered out.

D-22 exists because the 30 us gate has almost no headroom: hwlatdetect measured a 22 us firmware
floor on P-cores under load, leaving roughly 1 to 8 us for everything the kernel does. An
undecomposed total makes a miss uninterpretable, so the report shows both numbers.

Output: `nr-metrics` with a generated schema, a comparison with concrete thresholds, and report
rendering that a human reads.

Comparison rule, stated once and implemented exactly:

```
fail when observed > max(baseline * (1 + relative_pct / 100.0), baseline + absolute_us)
```

with `p99` and `max` checked independently and both reported. Compute in integer microseconds
with the relative term rounded down, so the boundary is deterministic and a reviewer can
reproduce it by hand.

`report::render_run_report(&RunManifest, &CyclictestRun) -> Result<String, ReportError>` produces
the per-run `REPORT.md` that plan 01-07 writes into every run directory. This is D-12's
"human-readable RIG.txt-style summary is generated from it rather than hand-maintained, so the
two cannot disagree". Sections, in this order:

  1. A header naming the run id, run class, instrument class, provenance tier, UTC start and end,
     and the blake3 of the manifest it was generated from.
  2. Rig and tuning, rendered from the manifest fields, in the same field order RIG.txt uses so
     a reader familiar with the existing artifact recognises it.
  3. Preconditions, as a table of check, status, observed, expected. All 14 rows, always.
  4. Contamination verdict, with the observed counter deltas per isolated CPU and the thresholds
     applied, or the word "uncalibrated" and the reason.
  5. Results, as a percentile table plus the sample count, the overflow count and the maximum.
  6. Distribution, as an ASCII histogram: one row per decade of count, or one row per bin band,
     fixed width, log scale on the count axis, with the axis labelled. OSADL publishes 1 us
     resolution on a logarithmic y axis and that is the convention to follow. Plot only bins with
     a non-zero count and state the bin range covered.
  7. Overflow convention, one paragraph, stating that overflow samples are recorded at the
     histogram bound as a lower bound and that percentiles at or above the overflow fraction are
     therefore conservative.
  8. Artifacts, as a table of path, bytes and blake3.

Publication decisions fixed here, since they were left to Claude's discretion:
  - Histograms are generated on demand from the raw capture, never committed as images. The
    repository holds no binary plot files. A reader who wants a plot has the raw `.hist` and the
    derived `hist.tsv` that plan 01-07 writes beside it.
  - The ASCII histogram in REPORT.md is the in-repo visual form. It diffs cleanly in review,
    which a PNG does not, and it satisfies BENCH-05's "histograms rather than means" without
    adding a plotting dependency.

`report::render_plat03_verdict(&Plat03Input) -> Result<String, ReportError>` renders the D-22
decomposition. `Plat03Input` requires both numbers:

```rust
pub struct Plat03Input {
    pub observed_max_us: u64,
    pub gate_us: u64,                  // 30
    pub firmware_floor_us: u64,        // from the D-18 hwlatdetect re-run on the RT kernel
    pub firmware_floor_source_run_id: String,
    pub p99_us: u64,
    pub p50_us: u64,
}
```

`firmware_floor_us` and `firmware_floor_source_run_id` are not optional. A PLAT-03 verdict
rendered without them returns `ReportError::FirmwareFloorRequired`. That is D-22 made mechanical:
the gate sits barely above a 22 to 29 us firmware floor, so an undecomposed number is
uninterpretable and the type refuses to produce one.

The rendered verdict states, in this order:
  - total observed maximum against the 30 us gate, and whether it is under
  - kernel contribution, computed as observed_max_us saturating_sub firmware_floor_us, named as
    "kernel contribution above the <floor> us firmware floor measured in run <run id>"
  - jitter, p99 minus p50, since that is the project's headline metric in later phases
  - the verdict word: "under the 30 us gate" or "documented limitation", never "fail" alone.
    ROADMAP.md success criterion 3 allows either outcome provided the residual is attributed, so
    the renderer must express the second outcome as a result rather than as a failure.
