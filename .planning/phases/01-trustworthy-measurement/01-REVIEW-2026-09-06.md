# Phase 1 review, 2026-09-06

Second adversarial review of Phase 1, taken after the D-18 re-take captures landed. The first
was `01-EXTERNAL-AUDIT.md` (2026-09-04), which drove the 15 to 23 plan expansion.

Every finding below was verified directly against the tree or the committed captures. Where a
claim originated from the reviewing model rather than from inspection, it was re-checked before
being written down; nothing here is recorded on assertion alone.

Verdict: Phase 1 is not ready to close. The four remaining plans as written do not satisfy its
five success criteria, and one defect makes plan 01-13 impossible to complete as specified.

## A. Blocks Phase 1 closure

### A1. No run can enter the series while thresholds are provisional

`config/contamination-thresholds.json` carries `"status": "provisional"`. In
`crates/cli/src/cmd/run.rs` the exclusion decision returns unconditionally:

```rust
if thresholds_provisional {
    return (true, Some(format!(
        "contamination verdict {verdict:?} was reached against provisional (D-24, not \
         yet calibrated) thresholds; ...")));
}
```

That `true` is `excluded_from_series`. Every one of the three D-18 re-take arms came back
`excluded_from_series: true` with that reason, despite all three being `Clean`.

Plan 01-13 requires `excluded_from_series=false` for the headline capture. Plan 01-14's weekly
comparison skips excluded entries. So the headline figure cannot be taken as planned, and the
weekly series would be empty even once it exists. Executing captures and installing a timer
cannot resolve this; it is a code and calibration problem sitting under two unexecuted plans.

The obvious fix is wrong. Flipping the status to `calibrated` would admit runs, but the D-24
classifier decides admissibility from the shape of the measured latency itself
(`crates/capture/src/interference.rs`, the tail-excursion and thread-max-spread predicates). A
genuine platform regression produces the same signature as contamination, so a real bad result
would be classified as contaminated and silently dropped from the series it exists to protect.
Run admission needs evidence independent of the number being measured.

This is the highest-value item in this document.

### A2. Orphaned tracer kthreads defeat TracersQuiescent

Recorded in full in `deferred-items.md` (2026-09-06 entry). `rtla` drives osnoise through its own
tracing instance, so the four top-level controls plan 01-18 widened all read quiescent while
osnoise sampling threads spin at SCHED_FIFO on the measured CPUs. This is not hypothetical: it
starved a real capture (`measurements/2026-09-06-precision3591-screen-02`, 75% of cyclictest
cycles lost, all six threads stalled at ~750000us, which is `osnoise/runtime_us`).

Success criterion 2 is that a third party can reproduce a run under documented conditions. A
precondition list that certifies a machine which is not quiet does not meet that. The current
mitigation is a guard in an operator-side script on the rig, which is explicitly not the harness
mechanism and does not travel with the repository.

Fix location: `crates/capture/src/preconditions.rs`. Both signals are readable without root: no
`osnoise`/`timerlat` kthread on any CPU in `--cpus`, and no live tracer in
`/sys/kernel/tracing/instances/`.

## B. Published claims that the captures do not support

### B1. "1 us on every isolated CPU" is false

`docs/rig/firmware-floor-rt-vs-stock.md` states the three arms "each report a maximum single
event of 1 us on every one of the six isolated CPUs". In the idle arm, CPU 7's final row in
`measurements/2026-09-06-precision3591-screen-03/rtla-hwnoise.txt` is:

```
  7 #899   674250000   0   100.00000   0   0   0   0
```

Max Single 0, HW 0, Noise 0, with full exposure. The supportable claim is that no isolated CPU
exceeded 1 us, a pooled observed maximum per arm. Assigned to plan 01-23.

### B2. The SMI bracket is described more tightly than it is

The same document describes the `MSR_SMI_COUNT` reads as immediately around each 900-second
hwnoise window. `crates/cli/src/cmd/run.rs` reads before cyclictest and again after hwnoise, so
the delta spans both instruments plus the environment snapshot. A zero delta over the wider
interval still supports zero during the screen, but the stated window is wrong. Plan 01-23.

### B3. A withdrawn figure is still used in derived claims

`measurements/2026-08-28-precision3591/README.md` carries a caveat (added by plan 01-19) stating
that the 7 us observation at a 1 us threshold has no raw capture in this repository, while the
same README continues to use that figure in its results table and in its "18x improvement"
claim. A number cannot be withdrawn in a footnote and relied upon in the same document. The same
README still asserts that SMI behaviour is kernel-independent and carries over to a PREEMPT_RT
install, which is precisely the untested assumption D-18 existed to test. Plan 01-23.

### B4. RES interrupts are published as "context switches"

`measurements/*/REPORT.md` renders a column headed `context switches`.
`crates/capture/src/interference.rs` documents that the field holds `/proc/interrupts` RES
rescheduling IPIs, because `/proc/stat`'s `ctxt` is a single machine-wide counter with no
per-CPU breakdown (the substitution was a deliberate, recorded choice in plan 01-05). The code
is honest; the published label is not. Rename the published quantity.

### B5. The hwnoise coverage caveat repeats the D-18 category of error

`crates/metrics/src/report.rs` renders: "a CPU absent from the observed list was sampled and
reported nothing, rather than never being sampled." Missing output does not establish that
sampling occurred. Idle CPU 7 above is the counterexample: a genuinely sampled CPU with zero
events still produces an explicit row carrying its exposure. A CPU missing from the output
should fail the coverage claim, not be explained away. This is the same shape of assumption
that made the 22 us figure wrong for two weeks.

## C. Harness gaps

### C1. Strict verification does not re-derive firmware figures

Plan 01-19 made `verify --strict` re-derive the cyclictest percentile table from the raw
histogram. It does not do the equivalent for firmware screens: `crates/cli/src/cmd/verify.rs`
knows `rtla-hwnoise*.txt` only as an artifact filename to checksum. A firmware maximum edited by
hand in a `REPORT.md` passes the gate. Given that the phase's headline new result is a firmware
figure, this is the least covered number in the repository.

### C2. Harness identity falls through on the rig

All three D-18 re-take manifests record `"git_sha": "unavailable-at-build-time"` with
`"git_sha_source": "unavailable"`. Plan 01-16 embedded the source revision at build time
specifically so a stale binary would be visible, but the rig has no `git` and `~/neurorust`
there is an rsync mirror with no `.git`, so `crates/cli/build.rs` takes its fallback branch.

This is honest rather than wrong, and strictly better than the defect 01-16 fixed (a read
failure recorded as `git_dirty: false`, asserting a clean tree nobody observed). But the captures
identify the executable by blake3 without establishing which committed revision produced it,
which is most of what the field was for. Options: install `git` on the rig, stamp the sha into
the rsync payload at push time, or record the dev-host sha that built the binary that was shipped.

## D. Defects in unexecuted plans

### D1. Plan 01-14's credential helper exposes the token it claims to protect

```sh
GIT_ASKPASS=/bin/true git -c credential.helper="!f(){ echo username=x-access-token; \
    echo password=$(cat $TOKEN_FILE); };f" push origin HEAD:refs/heads/main
```

The helper is in double quotes, so `$(cat $TOKEN_FILE)` is expanded by the invoking shell before
`git` runs. The token becomes part of git's argv and is visible in `ps`. The plan's own prose
immediately below claims it "does not appear in `systemctl show`, in the journal, or in `ps`".
That claim is false as written. Single-quote the helper so the substitution happens inside the
helper at git's invocation.

Separately, the refusal branch earlier in the same script pushes with no credential helper at
all, so the refusal path cannot authenticate.

### D2. Plan 01-12's non-reproduction branch overreaches

The plan instructs that a failure to reproduce the stall be attributed to "contamination rather
than the kernel", and derives a frequency bound from exposure alone. Non-reproduction establishes
neither causal exclusion nor a statistical bound without assumptions the plan does not state. The
three-cycle budget is sound and should be kept; the conclusions permitted at the end of it should
be narrowed to what non-observation actually supports.

## E. Success criteria against the remaining plans

| # | Criterion | Assessment |
|---|---|---|
| 1 | Named kernel path for the ~3.8 ms stall, with committed trace | Not guaranteed. 01-12 permits closing PLAT-01 on non-reproduction or an open question, neither of which names a path. |
| 2 | Third party can reproduce under documented conditions | Blocked by A2. The precondition list certifies a machine that is not quiet. |
| 3 | Under 30 us, or residual attributed to a named platform cause | Not guaranteed. 01-13 permits an unattributed residual as a documented limitation. |
| 4 | Every figure stamped, raw capture alongside, losing configurations retained | Partial. Retention works and is demonstrated. C1, C2, B4 and B5 remain. |
| 5 | CI commits a weekly metrics JSON | Not implemented, and blocked by A1. The plans also have the rig commit and CI judge, which is defensible but does not match the criterion's wording. |

Criteria 1 and 3 are worth an explicit decision rather than a silent pass: both permit an honest
"we could not determine this", and honest non-determination is not the same as the criterion
being met. Either revise the criteria to say what an acceptable negative result looks like, or
accept that the phase can close with them unmet and stated.

- New plan or extension of 01-18: A2, the tracer-quiescence gap.
