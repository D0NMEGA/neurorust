<objective>
Close the first half of audit finding 6: make a manifest identify the binary that produced it,
and make a recorded command line reconstructable rather than merely plausible.

Purpose: the project's core value is that every latency claim is reproducible from published raw
captures on a named rig. Three concrete defects stand between that sentence and the tree.

First, `crates/cli/src/cmd/run.rs:721` derives harness identity by shelling out to
`git rev-parse HEAD` in whatever the process's working directory happens to be. Seven of the
eight committed manifests record `"git_sha": "unknown", "git_dirty": false`, because the runs
were launched through `systemd-run` as root with no working directory inside the checkout. The
one manifest that does carry a sha carries the checkout's sha, not the binary's, so a stale
executable inherits a newer checkout's identity. A failure to read git is additionally recorded
as `git_dirty: false`, which asserts a clean tree that was never observed.

Second, `run.rs:441` relativizes the recorded argv against the final run directory while the
tools actually wrote into a `tempfile::tempdir()` under `/tmp`. The rewrite therefore matches
nothing, and every committed manifest carries a literal
`--histfile=/tmp/.tmpEb5CdX/cyclictest.hist` naming a directory that no longer exists. Neither
the executed command nor the committed artifact is recoverable from that.

Third, three of the defects the external audit found were a claim in prose that the code did not
implement, and the counter inversion in particular could have been caught the day it was written
because the correct numbers were already sitting in two committed manifests. A test that
re-derives a quoted figure from the artifact it is quoted from is the mechanical guard against
that whole class.

Runs entirely on the macOS dev host. No rig access, no captures.

Output: harness identity that describes the executable, an argv that describes what ran, and a
test that re-derives the published counter figures from the committed calibration pair.
</objective>

pub struct HarnessInfo {
    pub version: String,
    /// The commit the binary was BUILT from, embedded at compile time by
    /// `crates/cli/build.rs`. Never re-derived from the working directory at run
    /// time: a stale executable running inside a newer checkout would otherwise
    /// inherit that checkout's identity, and a run launched by systemd-run with no
    /// working directory inside the checkout would record "unknown". Both happened;
    /// see finding 6 of `01-EXTERNAL-AUDIT.md`.
    pub git_sha: String,
    /// Whether the working tree was dirty when the binary was built. Meaningful only
    /// when `git_sha_source` is `build-time`.
    pub git_dirty: bool,
    /// How `git_sha` was obtained. Absent on manifests written before this field
    /// existed. `Unavailable` means the build could not read git at all, and
    /// `git_dirty` says nothing in that case.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub git_sha_source: Option<GitShaSource>,
    /// Lowercase hex blake3 of the executable that produced this manifest, read from
    /// `std::env::current_exe()`. The only field here that identifies the binary
    /// itself rather than a checkout.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub executable_blake3: Option<String>,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub executable_bytes: Option<u64>,
    /// The commit of the checkout the harness was INVOKED from, when one could be
    /// read. Recorded separately from `git_sha` so a stale executable running inside
    /// a newer checkout is visible rather than disguised. Absent when the process had
    /// no git checkout as its working directory, which is the normal case under
    /// systemd-run.
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub invoked_from_git_sha: Option<String>,
}

#[serde(rename_all = "kebab-case")]
pub enum GitShaSource {
    BuildTime,
    Unavailable,
}

|----------|-------------|
| the executable -> the manifest it writes | The manifest is the claim about which code produced a figure, and until this plan it described a directory rather than a binary |
