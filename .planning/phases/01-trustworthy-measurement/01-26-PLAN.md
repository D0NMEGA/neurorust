<objective>
Make the phase's headline new result the best-checked number in the repository instead of the
least-checked one, and make two published statements true.

Purpose, in three parts.

**C1.** Plan 01-19 made `verify --strict` re-derive the cyclictest percentile table from the raw
histogram, so a published number is checked against the evidence rather than trusted because the
harness wrote it. It does nothing equivalent for firmware screens: `crates/cli/src/cmd/verify.rs`
knows `rtla-hwnoise*.txt` only as a filename glob for checksum and stray-file detection. A
firmware maximum edited by hand into a `REPORT.md` or a `manifest.json` passes the gate today.
The phase's headline new result is a firmware figure.

**B4.** `measurements/*/REPORT.md` renders a column headed `context switches`. That field holds
`/proc/interrupts` RES rescheduling IPIs, because `/proc/stat`'s `ctxt` is a single machine-wide
counter with no per-CPU breakdown and cannot fill a `Vec<CpuCounter>` at all. The substitution was
a deliberate, recorded choice in plan 01-05 and the code documents it honestly. The published
label does not.

**B5.** `crates/metrics/src/report.rs` renders "a CPU absent from the observed list was sampled
and reported nothing, rather than never being sampled". Missing output does not establish that
sampling occurred. The counterexample is already committed: idle CPU 7's final row in
`measurements/2026-09-06-precision3591-screen-03/rtla-hwnoise.txt` is
`7 #899 674250000 0 100.00000 0 0 0 0`, a genuinely sampled CPU with zero events still emitting an
explicit row carrying its full exposure. So a CPU missing from the output should fail the coverage
claim, not be explained away. This is the same shape of assumption that made the 22 us figure
wrong for two weeks.

**Two decisions this plan makes, both stated rather than assumed.**

The manifest field is renamed with a serde alias rather than left alone or renamed outright. New
manifests emit `rescheduling_ipis`; the twelve already committed keep `context_switches` and still
deserialise, because `#[serde(alias)]` is a recognised field name and `deny_unknown_fields` accepts
it. This is not a schema-version bump: `nr_manifest::validate` pins `schema_version == 1` and
bumping it would fail all twelve committed manifests under the blocking D-13 gate.
`config/contamination-thresholds.json`'s `context_switch_delta_max` is deliberately NOT renamed: it
names a genuinely different, still-unimplemented quantity (a real per-CPU context-switch source),
`res_delta_max` beside it already thresholds the RES counter, and the doc comment on
`CalibratedThresholds::context_switch_delta_max` already says exactly that. Renaming it would erase
a real distinction to fix a label that is already correct.

The eleven already-committed `REPORT.md` files are re-rendered rather than left with a correction
note. `REPORT.md` is generated from the manifest and the raw capture by `render_run_report`, and
`verify --strict` already re-derives part of it, so it is a derived artifact and regenerating it is
the honest correction, matching plan 01-23's own rule that a published figure is corrected where it
was published rather than superseded by a newer document beside it. Doing that by hand-editing
eleven generated files would set exactly the precedent plan 01-23 refused to set when it added
`nrmeasure attempt` rather than hand-edit an orphaned `ATTEMPT.json`. So this plan adds the command
instead.

Runs entirely on the macOS dev host. No rig access, no captures taken.

Output: firmware figures inside the strict gate, an honest published label, a coverage claim that
fails on absence, and a mechanism for correcting a published rendering.
