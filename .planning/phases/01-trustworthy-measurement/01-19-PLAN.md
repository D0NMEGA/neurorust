<objective>
Close the second half of audit finding 6: make verification check the numbers, not only the
checksums, and stop a failure to compute from becoming a published zero.

Purpose: `nrmeasure verify` today establishes that a manifest exists, that its artifacts are
present, and that their blake3 digests match. That proves a capture has not been corrupted since
it was recorded. It does not prove that the figures published beside it were derived from it.
The audit names three concrete gaps:

`crates/cli/src/cmd/verify.rs:406` reads
`compute_percentiles(&run_dir, manifest).unwrap_or((0, 0))`. A correctly hashed but malformed
capture therefore produces a row in `measurements/INDEX.md` reading `p99 0, max 0`, which is not
a missing value, it is a wrong one. A reader has no way to tell it apart from a run that really
did observe zero.

Strict verification never regenerates `REPORT.md` or `hist.tsv` and compares them, so nothing
mechanically ties the published percentile table to the committed histogram. Every number in
this repository's published reports is currently trusted because the harness wrote it, not
because anything re-derived it.

`crates/histogram/src/json.rs:83` reconciles the `--json` summary against the `.hist` file on
thread count and per-thread maxima, and stops there. Two files can agree on both while
disagreeing on how many samples were taken, which is the denominator under every percentile and
every over-gate fraction the project publishes.

Separately, finding 6's last bullet: `measurements/2026-08-28-precision3591/README.md:55` cites
six events and a 7 us maximum at a 1 us threshold as its detector-validity evidence, and no 1 us
raw capture exists anywhere in this repository. That claim is either recovered or marked as
lacking a published raw capture. It is fixed here rather than in the firmware plans because it
is a provenance defect, not a firmware finding.

Runs entirely on the macOS dev host. No rig access, no captures.

Output: verification that recomputes, an index that can say `unavailable`, a reconciliation that
counts samples, and one published claim honestly labelled.
</objective>

<threat_model>
## Trust boundaries

| Boundary | Description |
|----------|-------------|
| a checksummed capture -> a published figure | A matching blake3 proves a file is unchanged; it proves nothing about the numbers printed beside it |
| a computation failure -> the published surface | Every fallback value in a publication path is a claim nobody made |
| a prose claim -> its raw capture | The project's core value is that a claim is reproducible from a published capture, so a claim with no capture is the specific failure to catch |

## STRIDE threat register

| Threat ID | Category | Component | Disposition | Mitigation plan |
|-----------|----------|-----------|-------------|-----------------|
| T-1-52 | Repudiation | crates/cli/src/cmd/verify.rs, `compute_percentiles` | mitigate | The `(0, 0)` substitution is removed. A failure to parse yields `unavailable` in the index and a named problem under `--strict`, so a malformed but correctly hashed capture fails the blocking gate rather than publishing a zero that reads like a measurement. |
| T-1-53 | Tampering | measurements/*/REPORT.md and hist.tsv | mitigate | Strict verification regenerates `hist.tsv` byte for byte and re-derives every figure in the `## Results` block from the run's own `.hist`, using the `--histogram` bound recorded in the run's own argv. Editing a published percentile to a flattering value now fails CI, because the raw capture is the authority and the report is checked against it. |
| T-1-54 | Repudiation | the histogram bound used for re-derivation | mitigate | The verifier refuses to assume a bound. A run whose recorded argv carries no `--histogram=` is reported as not re-derivable with that exact reason. Assuming 400 would produce a re-derivation that agrees by construction and proves nothing, which is worse than declining. |
| T-1-55 | Repudiation | reconstructed run directories | accept | The 2026-08-28 reconstruction has no generated report to re-derive, by design under D-16. It is recorded as `not re-derivable: reconstructed run has no generated report` and counted separately in the verify summary line, so its weaker provenance stays visible rather than being quietly folded in with the harness-generated runs. |
| T-1-56 | Repudiation | measurements/2026-08-28-precision3591/README.md | mitigate | The 1 us detector-validity claim is relabelled as an unverifiable note with no published capture, and the retake is assigned to plan 01-23. Leaving it phrased as confirmation is the exact overclaim the project's core value forbids. |
| T-1-57 | Tampering | crates/histogram/src/json.rs, `reconcile` | mitigate | Sample-count agreement is added to the thread-count and maxima checks, so a truncated `.hist` paired with a complete `--json` summary is rejected at parse time rather than silently changing the denominator under every published percentile. |
